WHAT WAS WRONG
1. Single point of failure. The bias filter computes (float)log((double)x) on the GPU, and the CPU
   pipeline computes the same value with the host libm. They agree only when the two log
   implementations agree. The runtime therefore admitted only the environments that were audited
   offline when each GPU target was admitted: glibc 2.35, one libm GNU build ID per target and one CPU
   signature. The H200 node moved to Ubuntu 24.04.5 (glibc 2.39, libm d53fcbff...) on 2026-11-17, and
   every bias-dependent stage then reported "not attested".
2. A latent native bug turned that state into an abort. In the unattested case the post-filter returned
   early (every candidate marked CPU_REQUIRED) before it created its workspace. The sealed F2 compaction
   (ssv_cuda.cu, plan7_ssv_sequence_batch_compact_postfilter_f2) then raised "post-filter workspace is
   unavailable". The project's documented intent was that "all other environments retain candidates for
   CPU scoring".

DESIGN CHOSEN: self-attestation at first use, cached per environment
- The project's own attestation (hmmer_gpu oracle/bias_log_attestation.cu,
  results/cuda/bias-log-attestation-sm75.json) compared device and host log for all 2,139,095,039
  positive finite binary32 inputs and required zero mismatches. The CUDA extension now runs that same
  audit in process (plan7_bias_self_attest):
    - the device side is the production device function;
    - the host side is the libm log reached through the same symbol whose module supplies the build ID;
    - on zero binary32 mismatches the process registers the live libm build ID, the full CPU identity
      and the device target, and each later classification checks all three again.
- Aksha runs the audit once per environment (about 2.5 s on an H200 with 28 threads) and caches the
  record. The cache key covers the CUDA extension SHA-256, audit algorithm, glibc, libm build ID, CPU
  identity, device product, CUDA runtime, driver API level and nvcc build.
- A later process re-binds the cached record through plan7_bias_register_attestation. It refuses any
  record that differs from the live identity in build ID, CPU or target, or that is not a complete
  zero-mismatch audit.
- Built-in environments stay trusted without an audit. The device allow-list (H200, RTX 2080 Ti; CUDA
  12.5.82, runtime 12050) and the floating-point environment check are unchanged.
- The correctness policy is not weakened. The criterion is exactly the one that admitted the original
  targets; only where and when it runs changed.

Options rejected
- Adding d53fcbff to the allow-list after a manual audit: this fixes today and keeps the single point of
  failure for the next glibc update.
- Making results independent of the host libm, by vendoring one log implementation into both the
  private Easel/HMMER runtime and the device: this changes the CPU reference itself, needs a runtime
  rebuild and a full requalification, and departs from the project's rule that HMMER 3.4 with the host
  libm defines correctness.
- Auditing at every process start with no cache: it would be correct and cheap on the H200, but the
  readiness check could not answer without running on a GPU, and slower hosts would pay the cost on
  every search.
- Sampled or partial audits: these are weaker than the original exhaustive criterion.

Graceful degradation: when the bias math is untrusted (audit disabled or failed, or the device or host
is not admitted), the search continues exactly. The GPU runs only the SSV filter, and the bias filter,
Viterbi, Forward and domain stages run on the CPU pipeline. The search prints one warning line that
names what is untrusted and how to restore GPU use. Separately, the native fix lets the session route
complete through the host records (audit control ASTRA_GPU_UNTRUSTED_NATIVE_FALLBACK=1).

WHAT AN OS UPDATE DOES FROM NOW ON
- New glibc/libm, CPU, driver, CUDA runtime or a rebuilt extension: the key changes, so the first GPU
  search (or aksha gpu-check --attest) runs the 2.5-s exhaustive audit and caches it.
    - Zero binary32 mismatches: the GPU path continues with no other action.
    - Mismatches: the search completes exactly on GPU SSV plus the CPU, with one warning naming the
      mismatch count and the first input. The GPU then needs a different libm or device.
- A GPU product that is not admitted: SSV only, with a warning. Admitting new hardware is still a
  deliberate allow-list and audit step.
- In every case the result is either identical GPU output or an exact CPU fallback; no case aborts.
